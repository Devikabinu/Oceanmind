# Data Contracts — Modules 2, 3 and 4

This file is the **interface between Module 1 (data), Modules 2–4 (ML + alerts) and the
backend API / frontend**. The API and UI read the four tables below; the ML modules write
them. As long as the tables keep their shape, nobody has to wait on anybody else.

> **Status: the tables currently hold PLACEHOLDER data** (fake rows generated by
> `backend/app/db/seed_placeholder_contracts.py`). They are tagged so they can be told apart
> from real output — see [Placeholder data](#placeholder-data).

## Ground rules

1. **Batch, not live.** Each ML module runs as a **batch job** that reads Module 1's tables
   (`ocean_observations`, `biodiversity_observations`, `datasets`) and **writes directly to
   its tables below**. There is no live API call into any module's code; the backend only
   reads these tables.
2. **Changing a table = changing this file.** Anyone who wants to add, remove, rename or
   re-type a column, change an enum's values, or change what a field *means* must
   **update this file in the same change and flag it to the team first** — the API,
   frontend and the other modules all depend on it.
3. Schema changes go through an Alembic migration (`backend/alembic/versions/`), never by
   editing the database by hand.
4. Models live in `backend/app/models/`; enums in `backend/app/models/enums.py`.

## Who writes what

| Table | Written by | Read by |
|---|---|---|
| `sst_forecasts` | **Module 2** — SST forecasting | API/frontend, Module 4 |
| `anomaly_detections` | **Module 3** — anomaly detection | API/frontend, Module 4 |
| `ecological_risk_scores` | **Module 3** — ecological risk | API/frontend, Module 4 |
| `alerts` | **Module 4** — alerting | API/frontend (also updates `status`/`resolved_at` via the API) |

Module 4 runs **after** Modules 2 and 3 in the batch order, since alerts reference their rows.

Conventions shared by all tables: `id` is a UUID primary key (generate with `uuid.uuid4()`);
`created_at` is filled by the database (`now()`) — don't set it; all timestamps are
timezone-aware UTC; latitude is −90..90 and longitude is **−180..180** (same as Module 1).

## `sst_forecasts` — Module 2

One predicted SST value for one location and one future time.

| Column | Type | Null | Meaning |
|---|---|---|---|
| `id` | UUID | no | Primary key |
| `dataset_id` | UUID FK → `datasets.id` (CASCADE) | no | The ENVIRONMENTAL dataset the model was trained/run on |
| `timestamp` | timestamptz | no | The time the prediction is **for** (not when it was made — that's `created_at`) |
| `latitude`, `longitude` | float | no | Location of the prediction (decimal degrees) |
| `predicted_sst` | float | no | Predicted sea surface temperature, **°C** (same unit as `ocean_observations.sst`) |
| `forecast_horizon_days` | int | no | How many days ahead of the last input observation this prediction is |
| `model_version` | varchar(100) | no | Identifier of the model/run that produced the row |
| `created_at` | timestamptz | no | When the row was written (DB default) |

Indexes: `dataset_id`, `timestamp`, `latitude`, `longitude`, `(dataset_id, timestamp)`.

## `anomaly_detections` — Module 3

The anomaly verdict for one `ocean_observations` row.

| Column | Type | Null | Meaning |
|---|---|---|---|
| `id` | UUID | no | Primary key |
| `observation_id` | UUID FK → `ocean_observations.id` (CASCADE) | no | The observation that was scored |
| `timestamp` | timestamptz | no | Copy of the observation's timestamp (denormalized so maps/alerts need no join) |
| `latitude`, `longitude` | float | no | Copy of the observation's location (denormalized) |
| `anomaly_score` | float | no | **0..1**, higher = more anomalous |
| `is_anomaly` | bool | no | The model's final yes/no decision (the module owns its own threshold) |
| `model_version` | varchar(100) | no | Identifier of the model/run |
| `created_at` | timestamptz | no | DB default |

Indexes: `observation_id`, `timestamp`, `latitude`, `longitude`, `is_anomaly`.

## `ecological_risk_scores` — Module 3

The ecological risk assessed for one `biodiversity_observations` row.

| Column | Type | Null | Meaning |
|---|---|---|---|
| `id` | UUID | no | Primary key |
| `biodiversity_observation_id` | UUID FK → `biodiversity_observations.id` (CASCADE) | no | The occurrence record that was scored |
| `timestamp` | timestamptz | no | Copy of the observation's timestamp (denormalized) |
| `latitude`, `longitude` | float | no | Copy of the observation's location (denormalized) |
| `risk_score` | float | no | **0..1**, higher = higher risk |
| `risk_level` | enum `risk_level` | no | `LOW` / `MEDIUM` / `HIGH` / `CRITICAL` — bucketed from `risk_score` |
| `contributing_factors` | JSON object | no | Free-form explanation of what drove the score (factor name → value). Use `{}` if none. The UI shows the keys/values as-is. |
| `created_at` | timestamptz | no | DB default |

Indexes: `biodiversity_observation_id`, `timestamp`, `latitude`, `longitude`, `risk_level`.

> The seed data buckets `risk_score` as <0.25 LOW, <0.5 MEDIUM, <0.75 HIGH, else CRITICAL.
> Module 3 may choose its own cut-offs — `risk_level` is the authoritative value for the UI.

## `alerts` — Module 4

A notification raised from a forecast, an anomaly, or a risk score.

| Column | Type | Null | Meaning |
|---|---|---|---|
| `id` | UUID | no | Primary key |
| `alert_type` | varchar(50) | no | What kind of alert. Values in use: `SST_FORECAST_HEAT`, `SST_ANOMALY`, `ECOLOGICAL_RISK`. Free string — adding a new type needs no migration, but add it here. |
| `severity` | enum `alert_severity` | no | `LOW` / `MEDIUM` / `HIGH` / `CRITICAL` |
| `latitude`, `longitude` | float | no | Where the alert applies |
| `timestamp` | timestamptz | no | The time the alert is **about** (e.g. the anomalous observation's time, or the forecast's target time) |
| `message` | text | no | Human-readable description shown in the UI |
| `status` | enum `alert_status` | no | `NEW` (default) / `ACKNOWLEDGED` / `RESOLVED`. Module 4 inserts `NEW`; the API changes it afterwards. |
| `related_forecast_id` | UUID FK → `sst_forecasts.id` (SET NULL) | yes | Set for forecast-driven alerts |
| `related_anomaly_id` | UUID FK → `anomaly_detections.id` (SET NULL) | yes | Set for anomaly-driven alerts |
| `related_risk_id` | UUID FK → `ecological_risk_scores.id` (SET NULL) | yes | Set for risk-driven alerts |
| `created_at` | timestamptz | no | DB default |
| `resolved_at` | timestamptz | yes | Set when `status` becomes `RESOLVED`, otherwise NULL |

Normally exactly one of the three `related_*_id` columns is set. (Not enforced by a DB
constraint — an alert may legitimately combine sources later; update this file if so.)

Indexes: `alert_type`, `severity`, `status`, `timestamp`.

## Placeholder data

`python -m app.db.seed_placeholder_contracts` (run from `backend/`, with `DATABASE_URL` set)
fills all four tables with **fake** data, using real coordinates, timestamps and SST values
sampled from what Module 1 has ingested. It needs Module 1 data to exist first.

- `sst_forecasts` / `anomaly_detections` rows have `model_version = 'placeholder-seed-v0'`.
- `ecological_risk_scores` rows have `"placeholder": true` inside `contributing_factors`.
- `alerts` have messages starting with `[PLACEHOLDER]` and link to placeholder rows.
- `--reset` removes **only** those placeholder rows (real model output is left alone) and reseeds.

When a module's real output is ready: delete its placeholder rows (`--reset` does this for all
four tables), run your batch job, and make sure real rows use your own `model_version`.
